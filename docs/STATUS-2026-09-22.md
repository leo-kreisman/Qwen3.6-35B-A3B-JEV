# Status — streaming a 35B MoE from SSD under a hard RAM cap

**One line:** Qwen3.6-35B-A3B runs as a typed-decision scorer with expert weights
streamed from NVMe inside a **hard 8 GiB cgroup cap on x86 Linux** — no Apple Silicon,
no GPU, no resident 20 GB. Cold (page cache evicted, cap verified binding): **4 typed
decisions in 39.4 s**, down from **72.8 s** at first measurement.

## The measurement, and why it can be trusted

The trap that makes most "8 GiB + SSD" numbers meaningless: cgroup v2 charges file pages
to whichever cgroup faulted them *first*. On a big-RAM host the checkpoint is already
resident, so a fresh capped scope reuses it free and the cap never binds. Measured
evidence of the trap being **avoided**, not merely assumed:

| check | value |
|---|---|
| page cache before run | evicted via unprivileged `posix_fadvise(DONTNEED)` (`fincore` 19.5 G → 0) |
| `memory.peak` | **exactly 8 GiB** |
| `memory.events max` | **70,584** — the cap genuinely bound |
| correctness | decisions unchanged (4/4, same probabilities) — streaming costs time, not answers |

Verify with `/proc/<pid>/io read_bytes`, never wall-clock: a *warm* run can be faster than
a disk run, and that inversion is the tell.

## Results (cold, cache evicted, 8 GiB cap)

| criteria | time | read | prefill tok/s |
|---|---|---|---|
| 4 | 39.4 s | 41.0 GB | 23.0 |
| 8 | 66.7 s | 64.1 GB | 27.2 |
| 16 | 127.1 s | 128.3 GB | 28.6 |

Warm floor (no cap): 9.29 s. Resident serving: **~59 → ~38.5 s per call**. Realistic
latency on a busy workstation (12 competing threads): **~74 s**.

## Four findings that are not in the prior art we surveyed

(Counted honestly: **12 repositories cloned, 11 marked CERTIFIED** in
`OFFLOAD_PROJECTS_ANALYSIS.md`, but **~9 distinct engines** — `slipstream-dwijenpatel` is a
TurboFieldfare fork, `Mference` carries the same files verbatim, and
`Qwen-MoE-Router-exp` is a stub. Earlier revisions said "twelve surveyed engines"; that
overcounted.)

1. **Thread oversubscription — an expert-streaming decode wants MORE threads than cores.**
   A thread waiting on a page fault is *not runnable*, so the device queue starves. Cold
   sweep over one fixed pass: 6 threads 54.6 s → 8 → 50.4 → 12 → 47.9 → **16 → 38.4 s**
   (−29.6%), flat at 20. Reads unchanged (41.2–42.1 GB), so the win is pure scheduling —
   and it proves the decode is **not** purely I/O-bound. Knee at **4/3 of hardware
   threads**. Two shipped defaults were wrong.
2. **`n_ubatch`, not `n_batch`, is the parameter that decides I/O.** The default 512
   silently split a 908-token group into two ubatches, each re-walking all 40 layers.
   Setting `n_batch = n_ubatch = sequences × 512`: decode **67.0 → 42.0 GB**.
3. **Read amplification decomposed into two independent ~2.1× factors.** Routing selects
   9.3 GB; the same pass reads 19.3 GB at a 16 GiB cap (gather overfetch) and 41.0 GB at
   8 GiB (cap-driven intra-pass re-read). The cap factor is measured independently of any
   access-pattern theory — so the rewrite's payoff is bounded from evidence, not models.
4. **`llama_memory_seq_cp` SIGABRTs on this checkpoint** (`qwen35moe` is hybrid
   recurrent/attention), so branches cannot share a prefilled prefix KV — which is why
   batching costs 908 token-forwards and is 2× *slower* warm. Batching pays only in the
   I/O-bound regime.

Also found and fixed: a `score_shared` bug where context was cleared once before the group
loop, so callers sending more than `n_seq_max` criteria re-used sequence ids still holding
a longer prompt and got a hard `llama_decode failed`. Regression test added. Thread count
does **not** change logits (bit-identical); batching moves the winning probability by
≤0.001%, decision-stable on all four fixtures.

## Decode — measured 2026-09-22 (first generation number this project has)

Every figure above is a *prefill token-forward*; the scorer generates nothing. The decode
path had never been run because **no generation code existed** — `--max-tokens` is an
*input* prompt cap, not a generation length. `scripts/probes/probe_decode.py` closes that.

| run | tok/s | MB read / token | notes |
|---|---|---|---|
| cold, cache evicted, **8 GiB cap verified binding** | **3.67** | **212.6** | prefill 25 tok in 7.52 s / 9.82 GB; `memory.peak` exactly 8 GiB; `memory.events max` 25,499; load 19.87 s; 44.32 GB total process read |
| warm, no cap | **10.68** | 0 | the checkpoint is fully page-cached |

The predicted ceiling was 2.4 GB/s ÷ 566 MB/token ≈ **4.2 tok/s** and the measured cold
number lands under it at 3.67. 212.6 MB/token is *below* the 566 MB/token routed-set figure
because of intra-run cache hits. Both runs are lossless — identical logits.

## What this is not — do not claim it

- **It is not 23–29 tokens/s of output.** Those figures in the table above are
  *prefill token-forwards*; 3.67 cold / 10.68 warm is the real generation rate.
- **We do not yet beat Edge0.** The honest like-for-like is our **warm 10.68** against
  Edge0's **14.9**, a **1.4×** gap — not 3.5×. Edge0's 2.9 GB active on a *24 GB* box means
  its 14.9–17.7 is page-cache-warm too. The gap is an **algorithm** (prerouter + fixed
  staged slots), not a platform, and it ports.
- **Not "more efficient."** SSD offload measures at up to **12× the per-token energy** of
  HBM, with the SSD at 73–80% of total energy. Say faster, never more efficient.

## The gap, and the portable route across it

Edge0 does not read the routed expert set per token. From its own docs: a trained
**prerouter predicts the next token's routing one token ahead** so loading overlaps
generation, fixed **staged slots** hold the resident set, and `staged_replace` can override
routing to that set — *"turn 'tens of MB moved per step' into 'almost nothing moved per
step'."* That is an **algorithm, not MLX**, so it ports to llama.cpp.

**Next step.** The decode number now exists (3.67 cold / 10.68 warm), so the axis the goal
is stated on is measurable. The highest-leverage import is **speculative verification**
(SpecMoE: ~2.25× on SSD, 76.73% transfer reduction; MoE-SpeQ's "amortization roofline" —
maximise accepted tokens per byte of synchronous I/O). It attacks exactly our measured
212.6 MB/token, one verification pass fetching the **union** of experts for k draft tokens,
and **none of the surveyed engines does it**. See `docs/ARCHITECTURE-DECOMPOSITION.md` §11.

The endpoint also now exists: `resident/systemone_shim.py` implements the TypeSafe System
One contract locally, so a decision costs **one prefill pass, not N token-forwards**.
